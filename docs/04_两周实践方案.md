# 两周强化学习实践方案

## 1. 推荐做什么

当前重点已转为梯度机制与长程 Agent，正式训练候选优先采用 [小型代码修复 Agent 方案](07_长程Agent强化学习怎样实际训练.md)。本页保留数字游戏的完整实施预案与评估模板，作为框架暖场或资源受限时的备选；后文“主实验”和每日任务仍指这份数字游戏预案，不代表当前优先级。

原预案主实验：**用小型开放权重语言模型，在规则明确的数字组合游戏上进行 GRPO 类训练，观察固定推理预算下的成功率变化。** 对照包括 RL 与“筛选成功输出再 SFT”。

选择依据是实验设计判断：这个任务可以大量生成题目、精确验证、控制难度、保留未见组合，而且不需要从真人采集偏好或牌局。任务形式参考 TinyZero 的 Countdown 方向，但本方案的规则与配置独立定义。TinyZero 官方仓库已注明停止积极维护，并推荐使用 verl，因此只借鉴任务设计，不直接采用其旧安装命令。[^27]

**目标是展示能力变化，不承诺某个涨幅。** 一个值得报告的结果可以是：固定采样次数和 token 预算时，未见组合上的精确成功率上升，同时说明格式、长度、成本与失败类型如何变化。现阶段没有已测结果。

## 2. 任务选择比较

| 任务 | 反馈／数据 | 两周内的主要工作 | 对报告的价值 | 建议 |
|---|---|---|---|---|
| 数字组合／Countdown 变体 | 自动生成、精确算术验证 | 验证器、基线、训练与评估 | 清楚展示 LLM RL 闭环 | 默认主实验 |
| 小型函数生成 | 自动测试；需要可信参考函数 | 测试覆盖、隔离执行、题型划分 | 更直接连接编程能力 | 若已有代码环境，可替换主实验 |
| 文字房间／MiniGrid DoorKey | 可重置环境、终局成功 | 轨迹采集、多轮 mask、布局生成 | 展示智能体的多步决策与信用分配 | 主实验稳定后扩展 |
| Blackjack | 短回合，可模拟 | 传统策略／价值学习较简单 | 很好的 DQN／策略梯度暖场 | 低算力教学备选，不充当 LLM 能力实验 |
| Kuhn／Leduc 小型扑克 | 环境可自动模拟 | 不完全信息、对手与评价 | 展示博弈和随机策略 | 对扑克特别感兴趣时再选 |
| 完整德扑／斗地主 | 可模拟，无须依赖真人日志 | 方差、动作空间、对手非平稳 | 研究价值高，首轮归因困难 | 两周主实验不优先 |
| 真实仓库修复 | issue、仓库、测试容器 | 环境重建及慢测试成本较高 | 接近真实 agent 训练 | 已有基础设施才考虑 |

扑克的困难不只是“牌局太长、数据不好采”。在模拟器中可以自行采集；更难的是隐藏信息、收益方差、对手策略和评价口径。RLCard 与 OpenSpiel 提供这类环境及研究工具。对随机对手胜率变高，不等于接近均衡或不容易被利用；若游戏足够小，应结合平均收益、不同对手与可计算的 exploitability 等指标。[^32][^33]

## 3. 主实验的可检验问题

**问题：** 对一个已经能偶尔解对的语言模型，结果奖励驱动的训练，能否提高未见数字组合上的成功率？这种变化是格式适配、采样效率变化，还是在新的难度条件下也有收益？

建议提前写下三个分析目标：

1. 固定生成设置下，RL 后精确通过率相对起始模型是否提高。
2. 格式／规则合法率与合法输出内部的精确率是否分别变化。
3. 测试成本、输出长度和新组合／新难度表现是否恶化。

不把“出现自我反思措辞”“输出变长”“训练 reward 变高”单独视为推理提升证据。

## 4. 数据与验证器

### 4.1 明确任务规则

给定 3 或 4 个正整数与一个目标整数，只使用 `+ - * /` 和括号，每个给定数字恰好使用一次，构造等于目标的表达式。中间值允许有理数；除数不得为零；最终目标为整数。不允许额外常数、数字拼接、幂运算、变量或函数调用。

示例：数字 `[2, 3, 7, 8]`，目标 `24`，合法解为 `(7-3)*(8-2)`。这只是解释规则的固定例题，不作为训练后提升的证据。

推荐输出接口：一行 `<answer>表达式</answer>`；如果允许推理文本，必须在所有模型上保持同样协议，并且只从唯一答案区提取表达式。不要给出现 `<think>` 或“让我再想想”这类文字额外奖励。

### 4.2 题目生成

先生成数字集合和一棵合法算术表达式树，使用精确有理数算出目标，筛掉无效除法与不符合范围的目标。再用独立求解器枚举验证可解性。这样不需要用另一个付费模型生成训练标签，也不把答案推理轨迹提供给策略。

反向生成会影响题目分布，因此记录生成规则、运算符比例、目标范围及可行解数量。若从全部候选问题中筛出可解题，也要保存被筛选的规则。训练与评测用同一主规则但独立随机种子；OOD 另外定义，不能用训练过滤器不透明地挑容易题。

**建议起始规模，待基线校准：** 3,000 道训练题、256 道验证题、512 道冻结的同分布测试题、256 道 OOD 题。三数字题与四数字题按初始难度诊断分层，不要求固定比例一开始就正确。

### 4.3 数据划分

按数字多重集分组划分：把数字排序形成 canonical key，同一个数字多重集下的所有目标题只进入一个 split。这样不会出现仅调整数字顺序或换目标就跨集合的明显泄漏。重复数字按次数计算，不能用集合去重替代多重集。

OOD 可选其一作为主要检验：五数字组合；更大数字范围；或需要不同运算结构的题目。每增加一个变化都应单独报告，避免把多个因素同时改变后无法解释。保留题目生成种子、题目 ID、解法用于验证端，但不把解法发给模型。

### 4.4 验证器的最小正确性要求

- 仅解析允许的表达式 AST；拒绝名字、调用、属性访问、索引、幂运算与其他语法。
- 检查所有数字字面量与给定多重集严格一致；拒绝隐含新常数和拼接数字。
- 用精确有理数运算判断相等，避免浮点容差奖励漏洞。
- 明确负号规则：允许减法形成负中间值，不接受通过一元负号把一个正数字换成未给出的常数。
- 限制答案长度、AST 大小、整数位数、分子／分母大小；不使用 Python `eval` 执行模型文本。
- 拒绝多个互相矛盾的答案标签、未闭合标签、非有限值和除零。
- 单独记录 `parse_ok`、`numbers_ok`、`operations_ok`、`exact_success`、`truncated`。

需要覆盖的验证样例：合法解；少用数字；多用数字；重复数字；新增常数；只复述目标；除零；伪造标签；把计算藏在函数调用中；超长嵌套。这些检查直接影响奖励是否可信，值得认真验证。

### 4.5 奖励

主设置使用二值奖励：只有完整满足规则且精确等于目标才得 1，否则为 0。格式指标只记录，不单独奖励。

若初始输出格式差到训练全零，先在验证集做 prompt 协议校准；确需少量格式 SFT 时，保存原始模型与热身 checkpoint，明确后续“RL 增益”只比较同一个热身起点。不能把格式 SFT 与 RL 的总效果全部归因于 RL。

可选奖励消融是加入很小的规则合法性奖励，但它会改变目标，必须单独标注，并始终用二值整题成功率评价。不要一开始叠加一组看似丰富却难解释的奖励。

## 5. 模型和资源

下面是方案分档，**不是经过本机验证的显存适配或时长承诺**。显存取决于模型、精度、LoRA、序列长度、group size、生成引擎、reference 处理和优化器状态。

| 资源条件 | 起点 | 推荐任务范围 | 首先实测 |
|---|---|---|---|
| 仅本机／CPU，GPU 未定 | 验证器与题目生成；传统小策略暖场 | 不承诺正式 LLM RL | 环境正确性、少量本地推理可行性 |
| 单张约 24GB GPU | 0.6B–1.5B 模型、LoRA、短输出 | 数字游戏、小规模 pilot | 生成与反向同时运行的峰值显存 |
| 单张约 48GB GPU | 1.5B–3B、LoRA 起步 | 数字游戏或短函数 | 真实 tokens/s 与有效组比例 |
| 80GB 或多卡 | 可尝试 3B–7B 或更大并行批次 | 代码／多步扩展 | 环境吞吐、rollout 与训练资源分配 |

候选模型包括官方开放的 [Qwen2.5-1.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct) 和 [Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B)。这是小规模实验候选，不是最新模型排名。Qwen3 的 thinking 设置、chat template 与生成参数需要固定；选择 instruct 模型也意味着已有后训练，不能包装成纯基座 R1-Zero 复现。[^30][^31]

小模型不一定适合更难的 Countdown。TinyZero 的公开经验也对极小模型与较大模型作了区别，因此先测“是否存在偶尔成功的路径”，再决定缩短题目、换模型或增加热身，而不是盲目跑长训练。[^27]

### 5.1 框架选择

首选轻量单任务方案可使用 TRL 的 GRPOTrainer 与自定义奖励函数；如果需要多卡、复杂 rollout 或多轮环境，再考虑 verl。两者以官方文档和固定版本为准，不在资源不明时先搭完整分布式平台。[^28][^29]

必须显式记录 `loss_type`、奖励缩放、KL 系数、clip 配置、概率比粒度、组大小和最大回答长度。检索时 TRL 主线文档列出 `loss_type="dapo"` 默认值，不能因为类名为 GRPOTrainer 就称其为原始 GRPO。若选择 `dr_grpo`，其长度聚合设置与关闭题内标准差缩放是两个需要核对的设置。[^28]

### 5.2 试跑参数不是最终配方

建议 pilot 先考察：每题 4 个候选、最大输出 128–256 token、LoRA、保守学习率、少量 optimizer steps。全局生成批次必须与组大小兼容。具体 batch、学习率和 KL 初值在版本与硬件确定后从官方示例适配，不在文档里伪装成已验证的一键配置。

记录前 20–50 个更新的峰值显存、采样 tokens/s、每步总时长、验证器耗时、全对／全错组比例、entropy、KL 和截断率。如果训练侧 reward 改善而验证集没有对应变化，优先排查数据和评价，而不是直接延长时间。

### 5.3 用实测预算估算规模

若每步有 32 道题、每题 4 个候选、平均 256 个生成 token，则每步约 32,768 个生成 token；300 步约 983 万个生成 token。这只是算术规模，**不是显卡时长估计**，实际平均长度可能远小于上限。

先预算一个 50 万–200 万生成 token 的 pilot，再根据结果决定是否扩展。总成本还需加上评估、优化、参考策略／价值计算和失败重跑。用

\[
\text{预计 GPU 时间}\approx\text{实测平均每步时间}\times\text{计划步数}+\text{评估时间}
\]

估算，并保存单独的 rollout 与优化耗时。云端费用只在获得实际报价后计算，不复用旧项目的宣传成本。

## 6. 对照实验与评价

### 6.1 最小结果矩阵

| 配置 | 必须程度 | 回答的问题 |
|---|---|---|
| 起始模型，固定 prompt／生成设置 | 必须 | 未训练时有多强？ |
| 同一起点的 RL checkpoint | 必须 | RL 后是否改变？ |
| 起始模型增加采样预算 | 必须作为独立预算曲线 | 提升能否仅由多抽几次解释？ |
| 成功输出筛选后 SFT | 强烈建议 | 在线策略优化相对更简单方法有什么收益？ |
| 第二次独立 RL seed | 尽量保证 | 一次随机运行是否偶然？ |
| GRPO 与一个归一化变体 | 有余力再做 | 长度／难度权重如何影响训练？ |

成功筛选 SFT 应使用明确的数据来源。最省成本的初步对照是用起始模型采样、验证、保留成功输出；若使用 RL 过程中后期策略生成的数据，必须单独标记，不能声称是严格同源数据比较。分别记录生成 token、验证器调用次数、优化步数和 GPU 时间，而不是只对齐 epoch。

### 6.2 指标定义

**主指标：** 固定温度、top-p、token 上限和输出协议下的 sampled pass@1，即每题一次随机尝试的期望成功率估计。若每题独立采样 \(n\) 次、正确数为 \(c\)，可用 \(c/n\) 估计，再对题目平均。greedy 成功率另外报告，不能混称为同一个随机采样指标。

**预算曲线：** 对同一批题，报告 pass@1、pass@4、pass@8，并记录总 token 和运行时间。经典无偏估计式为

\[
\widehat{\mathrm{pass@}k}=1-\frac{\binom{n-c}{k}}{\binom{n}{k}},\qquad n\ge k.
\]

需要每题在固定采样分布下获取候选。该指标表示至少一个候选通过验证，不代表用户无需验证就能选出正确答案。[^18]

**辅助指标：** 规则合法率；合法输出中的准确率；平均与分位数输出长度；截断率；全零／全一组比例；每 1,000 个生成 token 的成功题数；OOD 成功率。若输出被截断，按预先定义规则计为失败或截断类别，不在看过结果后临时放宽。

**不确定性：** 测试题是聚类单位；同一道题的多个采样不是独立题目。训练前后使用同一题集，按题目做 paired bootstrap，计算成功率差的置信区间。训练 seed 的变化另列，不能用候选重复代替独立训练重复。

### 6.3 如何判定“明显提升”

在看到结果前，可把“同分布测试 pass@1 至少增加 10 个百分点、并有一致的跨 seed 方向”作为希望达到的展示目标；它是人为设定的目标，不是文献预测。如果真实改善只有几个百分点，按置信区间如实报告；如果只有格式提升，就明确称为输出协议适配改善。

最终 checkpoint 只按验证集选择。冻结测试集用于最终比较，不用来挑 prompt、奖励、模型或训练步数。验证阶段可以设停止规则：连续若干预先规定的评估点没有进步、输出长度异常增长或有效组几乎消失时，停止长跑并诊断。

## 7. 代码能力备选方案

如果更希望展示编程能力，可将主实验改为“短 Python 函数生成”。从参数化的小型任务族入手：列表变换、字符串处理、字典聚合、简单状态机；每类都有可信参考实现和隐藏随机测试。不要在短期内直接训练真实 GitHub issue 修复。

数据应按任务语义和模板族划分，不能只是同一模板换变量名跨训练／测试。初始模型准确率过高时增加组合操作，过低时减少题目跨度。公开 HumanEval／SWE-bench 用于理解评价，不直接用作调参题库。[^18]

执行模型代码必须在一次性隔离环境中：限制运行时间、内存和文件访问，禁用不需要的网络；隐藏验收器放在策略不可修改的位置。记录基础设施失败，避免把容器安装失败误记成模型逻辑失败。所有模型使用相同依赖和测试。

训练可用二值全通过奖励；若采用测试通过比例，明确区分平均用例通过率和整题通过率。最终用更强隐藏测试与不同输入分布检查投机解。无隔离执行条件时先完成环境，不在日常工作机直接运行任意生成程序。

## 8. 多步智能体任务扩展

推荐从文字版“找钥匙—开门—到达目标”开始，或者使用 MiniGrid DoorKey；第一版提供结构化观测和有限动作，以便分析多步决策。若已有可靠的代码执行或工具环境，也可以直接选取其中的短任务。[^34]

预先定义动作预算，例如先研究 8–16 次高层动作；动作粒度必须一致，不能把一次 `navigate_to(room)` 与一次原地转向当作可比步数。记录环境初态、每次观测、策略动作、工具响应、终局奖励和超时原因。

主奖励先采用终局成功 1、失败 0。训练集与测试集按地图布局和起点划分，使用从未出现的布局检验泛化。基础成功率太低时可以从更简单初态或较短路线课程开始；如果加入钥匙／开门中间奖励，确保单次事件只计分一次，并另报告无辅助奖励的终局成功率。

必须保存策略生成 mask。工具输出是观测，通常不进入策略动作损失。组内比较应控制任务与初态；多轮环境的随机性会污染相对优势，不能把不同地图上的回报直接当成同题比较。

这个实验支持的结论是多步决策在指定环境改善。后续扩展到代码修复或其他工具任务时，需要重新验证任务成功率、反馈可靠性和执行成本；小型环境的成功不能直接证明通用智能体能力。

|---|---|---|---|
| D1 | 09-12 | 确认 GPU、模型候选、任务；读 DQN／REINFORCE／PPO 关键部分 | 有明确任务规则与环境记录 |
| D2 | 09-13 | 生成器、独立验证器、划分与攻击样例 | 能自动检查正确／错误输出，split 无重复组 |
| D3 | 09-14 | 起始模型推理与难度校准 | 保存冻结 prompt、初始准确率、格式率、成本 |
| D4 | 09-15 | 固定框架版本，跑少量 rollout 和更新 | 权重更新链路可核对；保存 20–50 步日志 |
| D5 | 09-16 | 首次 pilot，诊断全零组与长度变化 | 决定继续、降难度或改模型；保留失败记录 |
| D6 | 09-17 | 第一轮正式运行 | 生成 token／GPU 时间与验证曲线完整 |
| D7 | 09-18 | 第二 seed 或修复已识别问题 | 中期检查是否有可信信号；不盲目追加算法 |
| D8 | 09-19 | 成功筛选 SFT 基线与采样预算曲线 | 能区分训练收益和更多推理预算的收益 |
| D9 | 09-20 | 冻结配置与 checkpoint；最终 ID／OOD 评估 | 评价不可反向用于调参；保存原始输出 |
| D10 | 09-21 | 有余力才做代码或多步扩展 | 主结果已稳定；否则集中解释主实验 |
| D11 | 09-22 | 图表、置信区间、典型成功与失败案例 | 无编造数字，分母／预算／版本齐全 |
| D12 | 09-23 | 填报告实验页，录屏和离线备份 | 展示无需现场重新训练或联网 |
| D13 | 09-24 | 完整计时彩排，调整删减页 | 82 分钟内容以内；公式与口头说法一致 |
| D14 | 09-25 | 最终核对与报告 | 结果冻结，保留代码、配置与日志 |

若 D5 仍没有训练信号，先检查验证器、输出协议和任务难度。若 D7 仍没有可信改善，报告可以诚实展示失败机制与修复尝试；不要用挑选的成功案例替代整体统计，也不要为了赶出上涨曲线把测试题放回训练。
