# 07｜把同样的训练机制接到开源预训练模型

代码：[07_pretrained_grpo.py](../code/07_pretrained_grpo.py)。这是手写单设备 LoRA GRPO 训练循环，保留生成、打分、优势与 log-prob 的可见性。它包含基线评估、训练、适配器保存和重新加载评估入口。

**更新：后续已在本机 CPU 上实际运行 Qwen2.5-0.5B-Instruct 的 GRPO＋LoRA，见 [手写 GRPO 实战](../../grpo_lab/README.md)。** 本课保留初版训练入口；后续实现补充了可恢复检查点、负载保护和独立测试。下面的微型 Qwen 冒烟记录是初版验证，不能与后续预训练权重结果混为一谈。

该冒烟检查已在本机通过：生成动作 log-prob 与重算值的最大差约 2.38×10⁻⁷，LoRA 梯度非零且完成一次参数更新。实测可选依赖版本见 [requirements-llm-tested.txt](../requirements-llm-tested.txt)，原始检查见 [check.json](../runs/pretrained_stack_check/check.json)。它核验的是随机微型 Qwen 的代码路径，不是 0.5B 预训练模型的性能或 CUDA 兼容性。

## 模型与任务为什么这样选

默认 [Qwen2.5-0.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct)，因为规模较小、具有标准 Transformers 接口；不是声称它是最新或能力最强的模型。默认 LoRA 只适配 Qwen 的 `q_proj`、`v_proj`，换架构时要核对模块名。

两个可选任务：四位数字字符串反转；两位数加法。都是完整答案的精确字符串判分，不执行模型代码，便于先把训练链路跑通。反转保留前导零：`1200 → 0021`，不能用整数解析把格式错误抹掉。

固定数据划分：1024 训练输入、128 验证、128 测试。加法用 a≤b 去掉交换重复；反转任务的不同输入可能共享同一个变换规则，这正是任务内泛化，不等于领域外泛化。所有划分保存在 `data_manifest.json`。

## 准备环境与基线

先激活课程 `.venv`。服务器需另建对应环境。

```bash
python -m pip install -r tutorials/requirements-llm.txt
python tutorials/code/check_pretrained_stack.py
python tutorials/code/07_pretrained_grpo.py --mode baseline --device cuda --out tutorials/runs/llm_baseline
```

会从 Hugging Face 下载所选权重与 tokenizer，缓存目录由其库管理。没有云 API 调用或租机操作。`--revision` 可指定已核验的模型 commit；默认 main 会变化，实际实验应保存并固定解析后的 commit、依赖版本与配置。

先查看 `baseline_validation_before.json` 的逐题文本。若已经全对，换难度或任务，不能再期待明显提升；若几乎全错，先判断是格式、任务难度还是提示问题。只有看到可学习的分布，才扩大训练预算。

## 训练与复测

```bash
python tutorials/code/07_pretrained_grpo.py --mode train --device cuda --steps 10 --out tutorials/runs/llm_smoke
python tutorials/code/07_pretrained_grpo.py --mode train --device cuda --steps 100 --out tutorials/runs/llm_train
python tutorials/code/07_pretrained_grpo.py --mode evaluate --device cuda --adapter tutorials/runs/llm_train/adapter --split test --out tutorials/runs/llm_test_trained
python tutorials/code/07_pretrained_grpo.py --mode baseline --device cuda --split test --out tutorials/runs/llm_test_base
```

两个 train 命令分别从基础模型重新开始；当前脚本没有断点续训功能。测试集只在确定方案后用于最终比较，不用它挑任务或超参数。`--device cpu`／`mps` 有入口，但大模型训练的设备兼容性与效率须实测；CPU 仅适合小规模排错。

## 一步训练到底做了什么

1. 选 2 个训练 prompt，每个生成 G=8 个候选，合计 B=16。
2. temperature=1、top-p=1、top-k=0，无重复惩罚，使生成分布与重新计算的原始模型概率一致。
3. 按完整字符串评分，按 prompt 分组计算优势。
4. 保存本批行为 log-prob；对当前模型重新前向，每条序列 microbatch=1 累积梯度。
5. 用 token 级 ratio 与 clip，每条序列按有效 token 数平均，再对 B 平均；一批做 2 次更新。
6. 只更新 LoRA 参数，基础权重冻结；结束保存 adapter，再用固定贪心设置评估。

LoRA 的线性层可写成 `y = Wx + scale * B(Ax)`。W 不更新，梯度更新小矩阵 A、B。它降低可训练参数与优化器状态成本，却没有免除经过基础网络的前向、反向激活计算，也没有改变任务本身。

## 容易导致“跑着但训错了”的位置

| 位置 | 本实现处理 |
|---|---|
| Prompt 与输出 | 只对 completion token 收集动作 log-prob |
| EOS／PAD | 第一个 EOS 参与动作损失，之后 padding 不参与，即使 PAD=EOS |
| 因果对齐 | 用前一位置 logits 预测下一个真实生成 token |
| 左侧 padding | attention mask 与 position ids 一起构造 |
| Dropout | rollout 与梯度计算都用 eval 模式；eval 不会禁用梯度 |
| 采样截断 | 最大生成长度是任务预算；没有 EOS 的输出按实际文本评分，记录逐题结果 |
| GRPO 全同分 | 优势为零；另外监控 informative group fraction |

使用 `.train()`／`.eval()` 控制 dropout，使用 `no_grad()` 控制计算图，二者不要混淆。

## 资源阶梯与实现限制

先在已有单张 GPU 上试 0.5B、短输出与小组数，再考虑 1.5B、更多候选或复杂任务。显存峰值还取决于词表 logits、序列长度、rollout batch、dtype 与优化器；这里不给未经测量的“某显存一定够”的承诺。

当前脚本为讲解而选择 eager attention、单设备、microbatch=1，没有量化、vLLM、分布式、异步、梯度检查点和断点续训。奖励序列均值与标准差归一化会影响训练权重；β=0 无参考 KL。生产实验再与 [TRL GRPO 文档](https://huggingface.co/docs/trl/grpo_trainer) 中的接口与损失变体对照，不直接复制一套配置当通用最优。

保存训练日志中的 reward、有效组比例，额外记录 GPU 峰值显存与墙钟时间。最终比较至少包含基础模型、RL 模型，以及用相同任务正确答案训练的 SFT 基线；当前预训练脚本只实现 GRPO，SFT 对照需另接训练器，不能伪装成已有结果。

下一步可改为函数输出预测、格式受约束的 SQL、受控代码修复。涉及生成程序执行时，需先建立隔离、超时、只读评分器和可重置环境，再谈算法扩展。
