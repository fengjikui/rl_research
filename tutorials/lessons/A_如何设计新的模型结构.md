# 专题｜既然都是反向传播，为什么还要设计不同结构？

## 1. 共用优化工具，不意味着模型等价

反向传播计算的是给定计算图与目标的导数。结构决定计算图、信息通路和参数共享，目标决定哪些输出被奖励，采样决定哪些情况被看到，优化与资源决定实际能走到哪里。

即便某类大网络在适当条件下具有通用逼近能力，也不意味着有限参数、有限数据、有限训练时间下容易学到想要的函数。可表示、可优化、可泛化、可部署是四个不同要求。

## 2. 模型结构首先决定能看见什么

如果只给当前一帧，网络可能根本看不到速度；如果输入摘要丢掉关键工具结果，后续层再复杂也恢复不了已经丢弃的信息。第 05 课的无记忆 MLP 正是这个例子。

设计前先问：答案依赖哪些信息？这些信息进入了输入吗？跨多远？是否只在很久以前出现？是否需要精确保存，还是压缩统计量就够？很多“模型不够强”的问题，实际是表示与接口没有提供所需信息。

## 3. 参数共享与信息交互方式

| 结构 | 主要计算与偏好 | 适合考虑的情况 | 代价与容易误解的点 |
|---|---|---|---|
| MLP | 固定坐标间的稠密混合 | 小型状态向量、固定特征、预测头 | 展平大图会丢掉显式邻域约束；不是不能学习图像 |
| CNN | 局部连接、空间共享 | 局部模式在多个位置复用 | 感受野与边界重要；平移等变不等于任务所需的不变 |
| RNN／GRU／LSTM | 共享状态更新，压缩历史 | 流式输入、固定状态预算 | 串行依赖、遗忘、压缩瓶颈；不保证无限记忆 |
| Transformer | 根据内容选择交互对象 | 变长上下文、跨位置关联、多模态序列 | 位置表示、mask、计算和 KV cache 成本需考虑 |
| GNN | 沿关系边传播并聚合信息 | 分子、关系网络、组合结构 | 依赖图构建；多层可能过平滑，表达能力受聚合限制 |
| 状态空间模型 | 用结构化状态更新处理序列 | 长序列与流式效率约束 | 状态压缩与精确检索能力需实测，非普遍优于 attention |
| MoE | 为输入选择部分专家计算 | 希望扩总容量而控制部分计算 | 路由、负载均衡、通信和利用率复杂；不是免费参数 |

这些是考虑因素，不是任务与结构的一对一配对表。图像也可用 Transformer，语言也可以使用不同序列骨干；最终要靠相同任务与资源约束下的证据。

## 4. “任务需要保留什么”，比套一个热门模块重要

识别图片中是否有猫，可能希望对位置移动不敏感；控制游戏挡板，恰恰必须知道球在左边还是右边。如果把空间信息过早做全局平均池化，某些需要位置的控制策略会更难表达。

又如两个工具结果之间的关联：长上下文 Transformer 可以直接访问先前 token，循环模型将其压缩到状态，外部检索可以只返回相关片段。三者是不同的信息访问与成本选择；不能只比较参数量后就下结论。

经典稠密全局 attention 的成对交互计算随序列长度呈二次增长；FlashAttention 一类实现改善内存访问与中间存储，并不把全局稠密交互本身自动变成线性计算。讨论“复杂度”必须说明指计算、训练激活还是推理缓存。

## 5. 结构也要服务于优化

残差连接提供较直接的信息与梯度通路，归一化影响激活尺度与训练稳定性，门控调节信息保留和更新。这些设计并不只是为了让模型理论上表达更多函数，也为了让优化器在现实预算下更容易训练。

但发现训练不稳定时，先查数据、学习率、目标尺度、mask、混合精度和终止逻辑。给错误 loss 加更复杂网络，可能只是更有效地拟合错误目标。

## 6. 区分结构、目标、训练算法和系统

| 名称 | 更准确的层级 |
|---|---|
| Transformer／CNN／GRU | 网络结构或模块 |
| 自回归语言模型 | 概率分解与建模方式，可以用不同序列结构 |
| Diffusion | 带噪过程、学习目标与生成方法；网络骨干可以不同 |
| GAN | 生成器与判别器的对抗学习框架；不是特定卷积结构 |
| SFT／DPO | 监督微调／偏好优化方式 |
| DQN／PPO／GRPO | 强化学习算法与目标估计／更新方案 |
| LoRA | 参数高效适配方式，可与不同目标组合 |
| Agent | 模型、工具、状态管理与控制流程组成的系统 |

同样的 Transformer 可做 next-token prediction、偏好优化或策略优化。相同 PPO 也可以训练 MLP 游戏控制器或 token 生成策略。因此比较两个“模型”时，应拆开这些维度，而不是只看产品名。

## 7. 一个可执行的新结构设计流程

**第一步：写清问题与资源。** 输入／输出的形状、信息依赖、实时性、长度分布、数据量、允许的延迟与显存。比如“100 次工具调用内记住关键测试失败原因”，比“做一个更强 Agent”可检验。

**第二步：复现简单基线，找具体失败。** 检查失败是否由信息丢失、表示不足、长依赖、样本覆盖、错误奖励或预算引起。先有诊断，再决定是否动结构。

**第三步：提出一个结构假设。** 例如“独立保存结构化测试摘要，会减少历史压缩后的回归错误”。同时列可能副作用：摘要丢细节、接口成本、检索错误。

**第四步：改最小必要模块。** 保留数据、目标、优化与评估，先验证改变的信息路径是否有效。若同时更换数据与损失，不能把全部增益归于结构。

**第五步：做消融与控制。** 同参数量只是一个口径，还需比较 FLOPs、训练墙钟、环境样本、推理延迟和可用上下文。给基线同等调参机会，做多 seed 并报告失败运行。

**第六步：测跨分布与实际成本。** 未见长度、位置、任务族、噪声、工具失败与上下文变化。一个模块在训练长度上提升不代表长程有效。

**第七步：决定是否值得保留。** 若同等预算下没有稳定收益，或工程代价大于收益，保留简单结构是合理结论。

## 8. 本系列可以怎样支持一次真正的研究练习

| 研究问题 | 起点 | 最小对照 | 不能直接声称 |
|---|---|---|---|
| 历史是否必要？ | 记忆线索 | 当前帧 MLP vs 全历史 MLP vs GRU | GRU 普遍优于 MLP |
| 空间共享有用吗？ | 接球 DQN | 同信息、近参数量、未见位置 | 一个 seed 的 CNN 更快就证明结构优越 |
| 是算法还是骨干起作用？ | 微型 LM | 固定初始化，换目标／固定目标换骨干 | 同样步数就是同样预算 |
| Agent 需要新结构吗？ | 工具查询 | 固定骨干，先改反馈和轨迹组织 | 所有长期任务都要更大 Transformer |

你最初的理解可以补成一句话：**我们共享的是求导与优化工具；不同模型真正不同的是信息如何表示和交互、什么行为被训练、训练分布怎样形成，以及用什么资源将这些过程实现出来。**

## 原始资料

- [Transformer](https://arxiv.org/abs/1706.03762)：内容相关的 attention 与序列建模。
- [ResNet](https://arxiv.org/abs/1512.03385)：深层网络与残差学习。
- [GCN](https://arxiv.org/abs/1609.02907)：在图关系上进行局部聚合。
- [Mamba](https://arxiv.org/abs/2312.00752)：选择性状态空间序列模型。
- [DDPM](https://arxiv.org/abs/2006.11239)、[GAN](https://arxiv.org/abs/1406.2661)：目标与生成框架不能简单等同于网络骨干。
- [LoRA](https://arxiv.org/abs/2106.09685)：冻结基础权重、训练低秩适配。
- [FlashAttention](https://arxiv.org/abs/2205.14135)：精确 attention 的 IO 与内存实现；[稀疏 MoE](https://arxiv.org/abs/1701.06538)：条件计算与专家路由。

表中的设计建议是围绕本教程的分析，不是声称这些论文证明了所有场景下的最优选择。
